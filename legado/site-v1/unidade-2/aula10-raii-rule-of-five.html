RAII e Regra dos Zero/Três/Cinco

🎯 Objetivos
  • Compreender a Regra do Zero, Três e Cinco
  • Decidir quando o compilador gera operações corretas vs. quando declarar manualmente
  • Implementar o idioma copy-and-swap para atribuição segura
  • Identificar vazamentos de recursos com AddressSanitizer
🎵
Sintonia — v1.1 — effect_chain com RAII

effect_chain armazena unique_ptr<effect>. A regra do zero em ação: nenhuma operação especial declarada — o compilador gera tudo corretamente.

§1

Regra do Zero

cpp Regra do Zero — deixe o compilador trabalhar 
// ✅ Regra do Zero: usa apenas membros que gerenciam si próprios
class track {
    std::string      name_;      // gerencia sua memória
    audio_buffer     buffer_;    // gerencia sua memória
    float            gain_ = 1.0f;
    bool             muted_ = false;
public:
    // SEM destrutor, SEM construtor de cópia, SEM atribuição
    // O compilador gera tudo corretamente — faça membros simples
};

// ❌ Evite: declarar destrutor sem necessidade
class track_errada {
    ~track_errada() {}  // agora cópia e movimento precisam ser declarados!
};
💡
Quando a regra do zero é impossível

Apenas quando a classe gerencia um recurso que não tem wrapper RAII: sockets, handles de arquivo C-style, handles de GPU. Nesses casos, encapsule em uma classe dedicada de RAII e use a regra do zero no resto.

§2

Regra dos Três e Cinco

OperaçãoGerada pelo compilador?Regra
Construtor padrãoSim, se nenhum outro declarado—
DestrutorSempreSe declara → declara os outros
Cópia (ctor + assign)Sim, se não há move declaradoRegra dos Três
Movimento (ctor + assign)Não se há destrutor declaradoRegra dos Cinco
cpp Quando declarar a Regra dos Cinco 
// Necessário quando você gerencia recurso manualmente
class raw_buffer {
    float* data_;
    std::size_t size_;
public:
    raw_buffer(std::size_t n) : data_{new float[n]}, size_{n} {}
    ~raw_buffer()                        { delete[] data_; }
    raw_buffer(const raw_buffer& o)      : data_{new float[o.size_]}, size_{o.size_}
                                         { std::copy(o.data_, o.data_+size_, data_); }
    raw_buffer& operator=(raw_buffer o)  { swap(*this, o); return *this; } // copy-and-swap
    raw_buffer(raw_buffer&& o) noexcept  : data_{o.data_}, size_{o.size_}
                                         { o.data_ = nullptr; o.size_ = 0; }
    raw_buffer& operator=(raw_buffer&& o) noexcept { swap(*this, o); return *this; }
};

LLMs neste Tópico

🤖
Prompt sugerido

"Implemente uma classe C++17 audio_file_handle que gerencia um FILE* com RAII. Aplique a Regra dos Cinco completa. Mostre por que o operador de atribuição usa o idioma copy-and-swap."

⚠️
O que o LLM costuma errar

LLMs frequentemente: (1) declaram o destrutor mas esquecem o move constructor, (2) não marcam o move constructor com noexcept, (3) implementam o operador de atribuição sem copy-and-swap, criando código não exception-safe.

Ex.

Exercícios Propostos

01.Usando o código do exercício llms/code-review-exercises/ex01_audio_buffer.cpp, identifique a qual 'regra' (0, 3 ou 5) pertence o bug. Aplique a regra correta.
02.A classe audio_buffer do Sintonia usa a Regra do Zero. Adicione um membro FILE* log_file_ = nullptr; sem alterar mais nada. O que acontece na cópia? Corrija o problema.
03.Implemente o idioma copy-and-swap para uma classe de sua escolha. Demonstre que a implementação é exception-safe mesmo se o construtor de cópia lançar.
04.Compile com -fsanitize=address um programa que viola a Regra dos Três (declara destrutor mas não cópia). Copie o objeto e observe o double-free. Corrija aplicando a Regra dos Cinco.
