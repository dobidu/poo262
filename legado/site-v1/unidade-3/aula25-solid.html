Os Cinco Princípios

LetraPrincípioEm uma frase
SSingle ResponsibilityUma classe, um motivo para mudar

S

SRP — Single Responsibility Principle

cpp ❌ Violação — audio_manager faz tudo 
// ❌ VIOLA SRP: 4 responsabilidades em 1 classe
class audio_manager {
    void load_from_file(const std::string& path);  // responsabilidade 1
    void apply_effect(const std::string& type);    // responsabilidade 2
    void save_to_file(const std::string& path);    // responsabilidade 3
    void print_stats();                             // responsabilidade 4
    // 4 motivos para mudar → 4 violações de SRP
};
cpp ✅ Correto — cada classe tem uma responsabilidade 
// ✅ SRP: responsabilidades separadas
class audio_processor  { void process(audio_buffer&); };
class audio_reporter   { void print_stats(const audio_buffer&); };
class project_repository { // ver DIP abaixo
    virtual void save(const project&, const std::string&) = 0;
    virtual std::unique_ptr<project> load(const std::string&) = 0;
};
O

OCP — Open/Closed Principle

cpp ❌ → ✅ via polimorfismo 
// ❌ VIOLA OCP: adicionar distortion exige modificar apply_effect
void apply_effect(const std::string& type) {
    if      (type == "gain")    applyGain();
    else if (type == "reverb")  applyReverb();
    // Nova linha obrigatória para cada novo efeito ← viola OCP
}

// ✅ OCP: hierarquia polimórfica — aberta para extensão
class effect {
    virtual void process(audio_buffer& buf) = 0;  // interface estável
};
class gain_effect    : public effect { void process(audio_buffer&) override; };
class reverb_effect  : public effect { void process(audio_buffer&) override; };
// Para adicionar distortion: cria nova classe, NÃO modifica código existente
class distortion_effect : public effect { void process(audio_buffer&) override; };
D

DIP — Dependency Inversion Principle

Módulos de alto nível (audio_engine) não devem depender de módulos de baixo nível (json_repository). Ambos devem depender de abstrações.

cpp DIP em ação — include/sintonia/io/project_repository.hpp 
// ── Abstração (alto nível depende disso) ──────────────────────────
class project_repository {
public:
    virtual void save(const project&, const std::string& path) = 0;
    virtual std::unique_ptr<project> load(const std::string& path) = 0;
    virtual ~project_repository() = default;
};

// ── Concreta para produção ────────────────────────────────────────
class json_repository : public project_repository {
    void save(const project&, const std::string&) override { /* JSON */ }
    std::unique_ptr<project> load(const std::string&) override { /* JSON */ }
};

// ── Concreta para testes — sem arquivo físico! ────────────────────
class memory_repository : public project_repository {
    std::unordered_map<std::string, project> store_;
    void save(const project& p, const std::string& k) override { store_[k] = p; }
    std::unique_ptr<project> load(const std::string& k) override {
        return std::make_unique<project>(store_.at(k));
    }
};

// ── audio_engine depende da ABSTRAÇÃO — injeção de dependência ───
class audio_engine {
    project_repository& repo_;   // referência para abstração
public:
    explicit audio_engine(project_repository& r) : repo_{r} {}
    void save_project(const project& p) { repo_.save(p, "projeto.json"); }
};
💡
Testabilidade como métrica de DIP

Se você não consegue testar audio_engine sem criar um arquivo no disco, DIP está sendo violado. Com DIP correto, injeta-se memory_repository nos testes — nenhum arquivo necessário.

SOLID e LLMs

🤖
Prompt de análise SOLID

"Analise o código abaixo e identifique violações dos cinco princípios SOLID. Para cada violação: (1) nomeie o princípio, (2) cite a linha problemática, (3) explique o impacto (o que fica difícil), (4) mostre o código refatorado. Mantenha C++17 e snake_case."

⚠️
LLMs erram frequentemente em

LSP: confundem com "override correto" — não é a mesma coisa. DIP: aceitam "usa abstração" sem verificar se a dependência ainda é concreta no ponto de construção. ISP: às vezes recomendam interfaces genéricas demais.

Exercícios Propostos
