Aula 06 · 14/mai

LLMs como Copiloto no Desenvolvimento OO

🎯 Objetivos
  • Usar LLMs de forma produtiva para modelagem, refatoração e testes
  • Reconhecer os padrões de erro mais comuns em código C++ gerado por LLM
  • Escrever prompts eficazes para C++17 OO
  • Estabelecer um workflow de revisão crítica
§1

Workflow de Desenvolvimento com LLM

TarefaEfetividade do LLMO que verificar
Esboço de classe (interface)⭐⭐⭐⭐⭐Convenções, const, noexcept
Implementação de método simples⭐⭐⭐⭐Regra dos 5, exceções
Testes Catch2⭐⭐⭐⭐Cobertura, Approx para float
Refatoração SOLID⭐⭐⭐LSP, ISP geralmente errados
Templates complexos⭐⭐Dedução de tipo, SFINAE
Concorrência⭐Race conditions sutis
💡
Use o LLM como par de programação, não como oráculo

O LLM é como um colega experiente que às vezes dorme na roda. Revise tudo, compile, teste com sanitizers.

§2

Anatomia de um Prompt Eficaz

text Estrutura recomendada 
Contexto:
  Projeto: Sintonia (mini-DAW em C++17)
  Convenções: snake_case, inglês, comentários PT, sem new/delete

Tarefa:
  [Descrição clara e específica]

Restrições:
  - C++17 (não C++20)
  - Sem includes desnecessários
  - Compilar limpo com -Wall -Wextra

Saída esperada:
  - arquivo.hpp com declaração

  - Comentários explicando cada decisão
§3

Padrões de Erro em Código Gerado por LLM

ErroFrequênciaComo detectar
Sem destrutor virtualMuito comumCompilar com -Wall
Object slicing em vectorComumTestar com ASan
PascalCase em vez de snake_caseMuito comumRevisão visual
new/delete em vez de unique_ptrComumgrep 'new '
Sem noexcept em moveComumChecar headers
Testes sem Catch::Approx para floatComumRevisar testes
⚠️
Veja os exercícios do repositório

Os arquivos sintonia/llms/code-review-exercises/ contêm código gerado por LLM com bugs reais para você identificar e corrigir.

🤖

LLMs neste Tópico

🤖
Prompt sugerido

"Revise o código C++17 abaixo e identifique: (1) todos os warnings que -Wall -Wextra emitiria, (2) comportamentos indefinidos, (3) violações de boas práticas C++ modernas. Para cada problema, cite a linha e proponha a correção."

⚠️
O que o LLM costuma errar

LLMs são auto-validadores ruins — tendem a dizer 'o código está correto' quando não está. Sempre compile você mesmo. Use o LLM para revisão, mas o compilador como árbitro final.

Ex.

Exercícios Propostos

01.Pegue o exercício llms/code-review-exercises/ex01_audio_buffer.cpp, sem olhar o gabarito, identifique todos os problemas. Compare com ex01_gabarito.md.
02.Use um LLM para implementar a classe reverb_effect seguindo a interface em include/sintonia/effects/effect.hpp. Compile com -Wall -fsanitize=address e reporte os problemas encontrados.
03.Escreva um prompt de revisão de código e aplique-o ao ex02_effect_chain.cpp. O LLM encontrou todos os 7 problemas do gabarito? Em qual ele falhou?
04.Explore: use um LLM para gerar testes Catch2 para audio_buffer. Quantos dos testes gerados já existem em tests/test_audio_buffer.cpp? Quantos casos não cobertos ele identificou?
