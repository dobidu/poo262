01

Funções virtuais, override, final e abstração

┌──┤▸ DERIVA · v1.1 · o despacho, e o destrutor que o acompanha├─────────┐

glifo() e nome() passam a puramente virtuais, o que torna entidade abstrata, e agir(mundo&) passa a virtual com corpo vazio. A base ganha virtual ~entidade() = default, e é essa palavra que a caça ao bug 2 retira para ver o que acontece.

A variante variantes/v1.1-quebrada/ traz a base com função virtual e destrutor não virtual. O que ela mede não é o vazamento, que é conhecido: é quando o compilador avisa.

└──────────┘
02

virtual, override e final

As três palavras respondem a perguntas diferentes. virtual, na base, diz que a chamada se resolve pelo objeto e não pelo ponteiro. override, na derivada, pede ao compilador que confira: se a assinatura não casar com nenhuma função virtual da base, o programa não compila, e é assim que um erro de digitação deixa de criar uma função nova em silêncio. final proíbe continuar sobrescrevendo, ou continuar derivando.

Na derivada, virtual não se repete: override já diz que a função sobrescreve, e diz melhor, porque o compilador o verifica. No Deriva, drone e item são final e sonda não é, e a razão dessa assimetria está na Aula 17.

┌──┤✓ DICA · Escreva sempre override├─────────┐

Sem override, trocar glifo por Glifo ou esquecer o const na assinatura produz uma função nova que ninguém chama, e o objeto passa a desenhar o glifo da base. O compilador não tem como saber que você queria sobrescrever, salvo se você disser. O item R5 da rubrica é a pergunta que pega isso na revisão.

└──────────┘
03

Classes abstratas e interfaces puras

Uma função puramente virtual, escrita com = 0, declara a operação e recusa fornecer o corpo. Basta uma para que a classe se torne abstrata e deixe de ser instanciável. Em entidade isso não é cerimônia: uma entidade sem glifo não significa nada no domínio, e a partir da v1.1 é o compilador que passa a dizer isso, em vez de a documentação.

Interface pura é o caso extremo: só funções puramente virtuais, nenhum dado, e destrutor virtual. É a forma que i_reparavel tem na v1.7, e a Aula 17 mostra por que ela é o único uso de herança múltipla que este material recomenda sem ressalva. A diferença entre "classe abstrata" e "interface pura" é a presença de estado, e é ela que decide se a herança múltipla vai duplicar alguma coisa.

┌──┤· NOTA · A abstração é afirmada, não descrita├─────────┐

O trecho extraído de testes/test_entidade.cpp afirma quatro decisões de projeto com std::is_abstract_v, std::is_constructible_v, std::has_virtual_destructor_v e std::is_copy_constructible_v. São perguntas respondidas em tempo de compilação: se alguém tornar a base instanciável ou copiável por acidente, o teste falha antes de o programa rodar.

LLMs neste tópico

┌──┤◇ LLM · Prompt sugerido├─────────┐

"Em C++17, snake_case: dada a base abstrata entidade, com glifo() e nome() puramente virtuais e agir(mundo&) virtual, escreva uma derivada concreta e um teste que afirme, sem executar nada, que a base é abstrata, tem destrutor virtual e não é copiável."

└──────────┘
┌──┤▲ ATENÇÃO · O que o LLM costuma errar├─────────┐

Erros recorrentes: override escrito numa função que a base não declarou virtual, o que ao menos falha na compilação; final posto na classe quando a intenção era pôr no método; e o destrutor da base declarado virtual sem corpo nem = default, o que passa da compilação e falha na ligação. Nenhum dos três aparece se você pedir o teste junto com o código.

8 bytes por OBJETO, não por classe. E o custo não desaparece quando a derivada acrescenta dado: ele se soma - 8 do vptr, 8 da posição, 4 da carga, 4 de padding.

cppinclude/deriva/leiaute.hpp · quanto custa o vptr
/// Sem nenhum método virtual: não há vtable, e portanto não há `vptr`.
struct entidade_simples {
  vetor2 pos;
};
struct drone_simples : entidade_simples {};

/// Com um método virtual: o compilador põe um ponteiro para a vtable como
/// primeiro campo do objeto. São 8 bytes por OBJETO, não por classe.
struct entidade {
  vetor2 pos;
  virtual ~entidade() = default;
  virtual void desenhar() const = 0;
};
struct drone : entidade {
  void desenhar() const override {}
};

/// E quando a derivada acrescenta dado, o custo do vptr não desaparece - ele
/// se soma. É a v1.2, quando o drone ganha carga.
struct drone_com_carga : entidade {
  int carga = 0;
  void desenhar() const override {}
};

static_assert(sizeof(entidade_simples) == 8, "só a posição");
static_assert(sizeof(drone_simples) == 8, "herdar de classe não-polimórfica é grátis");
static_assert(sizeof(entidade) == 16, "8 do vptr + 8 da posição");
static_assert(sizeof(drone) == 16, "a derivada sem dado novo não cresce");
static_assert(sizeof(drone_com_carga) == 24, "8 vptr + 8 pos + 4 carga + 4 de padding");

TEST_CASE("o despacho virtual escolhe pelo tipo do OBJETO") {

  const item i({3, 3}, "celula-de-energia", 5);

`virtual` não se repete na derivada: `override` já diz que sobrescreve, e diz melhor, porque o compilador o verifica.

cppinclude/deriva/entidade.hpp · `final` na folha, `override` nas sobrescritas
/// Drone de patrulha. Anda sozinho, em linha, e inverte ao bater.
class drone final : public entidade {
 public:
  inline static int vivos = 0;
  inline static int criados = 0;

  explicit drone(vetor2 pos, vetor2 rumo = {1, 0}) noexcept
      : entidade(pos), rumo_(rumo) {
    ++vivos;
    ++criados;
  }
  ~drone() override { --vivos; }

  [[nodiscard]] char glifo() const override { return 'd'; }
  [[nodiscard]] std::string_view nome() const override { return "drone"; }
  void agir(mundo& m) override;

  [[nodiscard]] vetor2 rumo() const noexcept { return rumo_; }

 private:
  vetor2 rumo_;
};

`is_abstract_v`, `!is_constructible_v`, `has_virtual_destructor_v` e `!is_copy_constructible_v`. Quatro decisões de projeto que o compilador guarda.

TEST_CASE("entidade e abstrata, e o compilador diz isso") {
  static_assert(std::is_abstract_v<entidade>);
  static_assert(!std::is_constructible_v<entidade, vetor2>);
  static_assert(std::has_virtual_destructor_v<entidade>);
