02

QObject, o MOC e a posse por árvore

A macro Q_OBJECT na declaração da classe exige o MOC, um pré-processador que lê o cabeçalho e gera código a partir dele: é ele que dá a cada classe um nome consultável em tempo de execução e registra os slots. É por isso que CMAKE_AUTOMOC existe, e é o que faz esta classe precisar de um sistema de build que entenda Qt - compilar o .cpp à mão não basta.

Um slot é um método comum que o MOC registra para poder ser chamado por nome, sem que quem chama conheça o tipo de quem recebe: é a versão do Qt para o Observer da Aula 25. A ligação se faz com connect, e a forma que o esqueleto usa passa ponteiro de função membro, que o compilador verifica. A forma antiga, com as macros SIGNAL e SLOT, casava strings em tempo de execução, e um erro de digitação virava conexão que nunca acontece, sem um aviso.

┌──┤▲ ATENÇÃO · Posse no Qt é a exceção declarada à regra da Aula 12├─────────┐

QObject tem árvore de pais, e o pai destrói os filhos. Passar um QWidget* cru ao construtor do filho entrega a posse ao pai, de forma que std::unique_ptr sobre QWidget com pai é dupla liberação. A regra do semestre - posse declarada no tipo - vale, e esta é a exceção, que fica escrita no cabeçalho em vez de escondida.

As duas formas convivem na mesma função: new QPlainTextEdit(this) entrega o visor à árvore do Qt, e o std::unique_ptr guarda a tela_qt, que é nossa e não é QObject. Dentro da tela_qt, o ponteiro para o visor é cru, porque é observação e não posse - o mesmo critério de mundo::primeira_com.

Separação domínio e apresentação, e o ponto de composição

CamadaResponsabilidadeDepende de
Domínio: mundo, entidade, mapaEstado do setor, turno, regra de movimentoC++17 e a STL, e nada mais
Apresentação: i_apresentacaoA interface que o núcleo conheceNada: é abstração pura
Implementações: apresentacao_em_texto, tela_qtDesenhar, cada uma no seu destinoA interface, e o Qt6 no caso da segunda
Persistência: partidaSalvar e carregar, com a versão do formatoA STL, e o texto que o replay já compara
Composição: main.cpp e qt/main_qt.cppEscolher as concretas e ligá-lasTodas as camadas, e é o único lugar que pode

A última linha é a que importa: existe um lugar autorizado a conhecer todas as camadas, e é o ponto de composição. qt/main_qt.cpp carrega o mapa, monta o mundo, acrescenta a sonda e entrega o mundo pronto para a janela; o mesmo mundo que o executável de terminal usa, montado do mesmo jeito.

O critério de aceitação da aula é verificável sem Qt instalado, e é isso que o torna útil: testes/test_padroes.cpp monta duas implementações de i_apresentacao no mesmo processo, sobre o mesmo mundo, e confere que desenhar cinco vezes não altera o estado do domínio - despejo byte a byte igual. Se desenhar mudasse estado, a segunda interface veria um sistema diferente da primeira, e a separação seria mentira.

`QObject` tem árvore de pais, e o pai destrói os filhos: passar um `QWidget*` cru ao construtor do filho ENTREGA a posse. `unique_ptr` sobre `QWidget` com pai é dupla liberação. É a exceção à regra da Aula 12, e ela é declarada, não escondida.

cppqt/janela.hpp · posse no Qt é a exceção declarada
/// A janela.
///
/// **Posse no Qt é diferente.** `QObject` tem árvore de pais, e o pai destrói
/// os filhos. Passar um `QWidget*` cru para o construtor do filho ENTREGA a
/// posse ao pai - e por isso `unique_ptr` sobre `QWidget` com pai é erro de
/// dupla liberação. É a exceção à regra da Aula 12, e ela é declarada e não
/// escondida.
///
/// O `Q_OBJECT` exige o MOC, um pré-processador que gera código a partir do
/// cabeçalho. É por isso que `CMAKE_AUTOMOC` existe, e é o que faz esta classe
/// precisar de um sistema de build que o Qt entenda.
class janela : public QMainWindow {
  Q_OBJECT

 public:
  explicit janela(mundo w, QWidget* pai = nullptr);
  ~janela() override;

 private slots:
  /// Um slot é um método comum que o MOC registra para poder ser chamado por
  /// nome, sem que quem chama conheça o tipo. É a versão do Qt para Observer,
  /// e o compilador não verifica a assinatura - o erro aparece em execução, na
  /// forma de uma conexão que não acontece.
  void ao_mover_norte();
  void ao_mover_sul();
  void ao_desfazer();

 private:
  void redesenhar();

  mundo mundo_;                          // o núcleo, intacto
  historico historico_;                  // Command, da v2.6
  std::unique_ptr<tela_qt> tela_;
  QPlainTextEdit* visor_ = nullptr;      // filho: o Qt é o dono
};

Ele implementa a mesma interface que `apresentacao_em_texto`, e o núcleo não sabe qual das duas está do outro lado. O widget é guardado como ponteiro cru porque é observação: a árvore do Qt é a dona.

cppqt/janela.hpp · o adaptador, que não é QObject
/// A implementação Qt de `i_apresentacao`.
///
/// Repare no que ela NÃO faz: não conhece regra de jogo, não decide o que
/// acontece num turno, não sabe o que é uma parede. Ela recebe um `mundo` e
/// desenha. É a mesma interface que `apresentacao_em_texto` implementa, e o
/// núcleo não sabe qual das duas está do outro lado.
class tela_qt final : public i_apresentacao {
 public:
  explicit tela_qt(QPlainTextEdit* alvo) : alvo_(alvo) {}

  void desenhar(const mundo& m) override;
  void mensagem(std::string_view texto) override;

 private:
  QPlainTextEdit* alvo_;   // observação, não posse: a árvore do Qt é a dona
};

`new QPlainTextEdit(this)` entrega a posse ao pai, e `unique_ptr` sobre o adaptador guarda o que é nosso. As duas formas convivem na mesma função, e a diferença está em quem destrói.

cppqt/janela.cpp · `new` com pai ao lado de unique_ptr
janela::janela(mundo w, QWidget* pai)
    : QMainWindow(pai), mundo_(std::move(w)) {
  visor_ = new QPlainTextEdit(this);   // `this` é o pai: o Qt destrói
  visor_->setReadOnly(true);
  visor_->setFont(QFont("IBM Plex Mono", 12));
  setCentralWidget(visor_);

  tela_ = std::make_unique<tela_qt>(visor_);

  QMenu* menu = menuBar()->addMenu("Sonda");
  QAction* norte = menu->addAction("Norte");
  QAction* sul = menu->addAction("Sul");
  QAction* desfazer = menu->addAction("Desfazer");

  // A conexão por ponteiro de função é a forma verificada em compilação. A
  // forma antiga, com as macros SIGNAL e SLOT, casava strings em execução - e
  // um erro de digitação virava conexão que nunca acontece, sem aviso.
  connect(norte, &QAction::triggered, this, &janela::ao_mover_norte);
  connect(sul, &QAction::triggered, this, &janela::ao_mover_sul);
  connect(desfazer, &QAction::triggered, this, &janela::ao_desfazer);

  redesenhar();

TEST_CASE("duas apresentacoes sobre o MESMO mundo, e ele nao sabe qual") {
  zerar_entidades();
  mundo w = montar();
  w.acrescentar(std::make_unique<sonda>(vetor2{1, 1}));

  // (2) Duas implementações independentes da mesma interface, no mesmo
  //     processo, sobre o mesmo mundo. É o que a v2.7 faz com Qt, e o que a
  //     variante `v2.6-antes` torna impossível.
  apresentacao_em_texto a;
  apresentacao_em_texto b;
  i_apresentacao& como_a = a;
  i_apresentacao& como_b = b;

  como_a.desenhar(w);
  como_b.mensagem("segunda interface");
  como_b.desenhar(w);

  REQUIRE(a.acumulado().find("entidades 1") != std::string::npos);
  REQUIRE(b.acumulado().find("> segunda interface") == 0);

Cinco renders, e o despejo byte a byte igual. Se desenhar mudasse estado, a segunda interface veria um sistema diferente da primeira.

cpptestes/test_padroes.cpp · desenhar não altera o mundo
TEST_CASE("trocar a apresentacao nao muda o estado do dominio") {
  // (3) O critério mais forte: desenhar não pode alterar o mundo. Se
  //     desenhar mudasse estado, a segunda interface veria um sistema
  //     diferente da primeira.
  zerar_entidades();
  mundo w = montar();
  w.acrescentar(std::make_unique<sonda>(vetor2{1, 1}));
  const std::string antes = w.despejar();

  apresentacao_em_texto tela;
  for (int k = 0; k < 5; ++k) tela.desenhar(w);

  REQUIRE(w.despejar() == antes);   // byte a byte, depois de cinco renders
}
